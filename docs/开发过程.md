# 开发过程

本文档只记录当前代码已经落地的开发路径，不再沿用旧版“完整平台蓝图”的写法。

## 1. 当前仓库的实际演进方向

项目最初目标覆盖灵感采集、AI 生成、人工审稿、自动发布、统计看板等完整链路，但目前真正成型并且前端主路径最完整的，是“工作台式写作流程”：

`首页 -> 建档向导 -> 工作台 -> 章节生成/编辑 -> 审阅 -> 发布`

因此近阶段开发重点已经从“功能铺面”转向“工作台闭环”，包括：

- 让用户能从一句灵感快速建档
- 把设定资产和章节资产聚合到一个工作台上下文里
- 支持 WebSocket 流式写作
- 让人工改稿、审阅、质量提醒直接围绕章节发生

## 2. 分层实现方式

### 2.1 前端

前端位于 `frontend/`，当前真正对外的页面只有：

- `Login`
- `Dashboard`
- `HomePage`
- `WorkspacePage`

`Dashboard` 负责路由、书目加载、工作台数据切换、建档向导弹窗和 LLM 配置弹窗。

主要职责拆分如下：

- `HomePage`：书目概览和建档入口
- `NewBookWizard`：草稿向导
- `WorkspacePage`：三栏式工作台
- `WritingCenter`：正文编辑与生成流
- `SettingsPanel`：右侧情报和审阅区
- `ChapterSidebar`：章节轨

### 2.2 Django

后端主业务在 `backend/apps/`：

- `users`：登录、刷新、用户统计
- `novels`：草稿、项目、设定、工作台聚合
- `chapters`：章节、审阅、发布、工作流分析
- `llm_providers`：模型配置
- `stats`：统计聚合
- `tasks`：任务查询
- `inspirations`：灵感采集和生成
- `publishing`：发布相关数据
- `monitoring`：健康检查

### 2.3 FastAPI

`fastapi_service/` 负责两类事情：

- HTTP 生成与分析接口
- WebSocket 流式接口

当前三组核心路由：

- `routers/ai_generate.py`
- `routers/ws_generate.py`
- `routers/ws_chapter.py`

### 2.4 Celery

Celery 使用 `backend/celery_app.py` 作为入口，主要承担：

- 异步生成章节
- 异步发布
- 定时抓取灵感
- 定时统计更新

## 3. 数据模型是怎么逐步收敛的

### 3.1 建档阶段

为了避免用户一开始就创建正式项目，当前实现采用了草稿态：

- `NovelDraft`
- `DraftSetting`

用户先输入一句灵感，系统建立 draft，再逐步补齐：

- 书名
- 世界观
- 人物
- 地图
- 故事线
- 情节弧
- 开篇

完成后再转化为：

- `NovelProject`
- `NovelSetting`

这个设计的好处是：

- 向导中途可以反复保存
- 正式项目不会被半成品污染
- 后续工作台只消费“已完成建档”的项目

### 3.2 写作阶段

写作阶段的核心模型是：

- `Chapter`
- `ChapterSummary`
- `ChapterReview`

章节本身存：

- AI 原稿 `raw_content`
- 人工稿 `final_content`
- 生成元数据 `generation_meta`
- 生成快照 `context_snapshot`
- 一致性状态 `consistency_status`

随后由工作流分析补齐：

- 摘要
- 开放线索
- 质量问题
- 一致性提醒

### 3.3 资产阶段

为了让右侧情报区不是纯静态设定，项目层又补了几类资产：

- `Storyline`
- `PlotArcPoint`
- `KnowledgeFact`
- `ForeshadowItem`
- `StyleProfile`

这些模型不是单独页面主导，而是通过 `build_workbench_context()` 聚合回工作台。

## 4. 工作台聚合是怎么形成的

工作台不是前端分别打十几个接口拼出来的，而是 Django 通过 `build_workbench_context()` 统一组装。

当前返回内容包括：

- 项目信息
- 聚合统计
- 章节列表
- 设定列表
- 章节摘要
- 章节审阅
- 故事线
- 情节点
- 知识事实
- 伏笔账本
- 章节资产索引
- 风格画像
- 工作台高亮
- 知识图谱

这样做的直接收益是：

- 前端切换项目时只拉一次大上下文
- 右栏和中栏可以共用同一份工作台快照
- WebSocket 保存章节后只需要重新刷新当前项目上下文

## 5. WebSocket 写作链路

这一块是当前系统最关键的“产品感”来源。

### 5.1 设定流

`useSettingStream` 连接：

- `WS /ws/generate-setting`

它把向导过程做成边生成边显示，最终写回 draft setting。

### 5.2 章节流

`useChapterStream` 连接：

- `WS /ws/generate-chapter`

支持：

- 单章生成
- 续写
- 重写
- 连续迭代

FastAPI 在流式生成的同时，会调用 Django 的：

- `POST /api/chapters/generate-from-ws/`

把结果直接保存成章节草稿，并同步摘要、一致性、审阅初始记录等工作流资产。

## 6. 审阅和流程闸门是怎么补上的

当前写作流程不再是“生成完直接发布”，中间插入了一个最基本的质量闸门。

关键规则在 `backend/apps/chapters/services/workflow.py`：

- 上一章还在生成中时，不能继续推后续章节
- 上一章缺少审阅记录时，会提示或阻塞
- 上一章状态是 `revise` 时会阻塞
- 人工改稿率低于 `15%` 时，不能标记已定稿，也不能发布

这部分让工作台从“AI 连续吐字”升级成“有基本质量约束的写作流程”。

## 7. 前端界面收敛过程

近期界面调整主要围绕工作台进行。

### 7.1 三栏结构固定

`WorkspacePage` 现在固定为三栏：

- 左：章节轨
- 中：正文工作区
- 右：情报区

通过 `react-resizable-panels` 支持宽度调节。

### 7.2 中部滚动修复

之前工作区里“实时写作 / 当前正文 / 流程日志”存在上下滑动异常，原因是外层容器高度链断裂、多个容器重复抢滚动。

本轮通过下面的方式修正：

- 父子容器统一补齐 `flex` 和 `min-h-0`
- 让内容区拥有明确的 `overflow-y-auto`
- 避免 Tabs 外层再包一层不可控滚动

### 7.3 右栏去重合并

参考右栏信息结构后，重复区域被合并到现在的 6 个标签：

- `作品设定`
- `世界观`
- `知识库`
- `手稿道具`
- `质量守护`
- `故事演进`

其中：

- 审阅定稿归入 `质量守护`
- 知识图谱归入 `知识库`

这次收敛的目标不是加模块，而是让右栏减少重复、逻辑更清晰。

## 8. 启动与运行形态

### 8.1 Docker 形态

`docker-compose.yml` 当前服务为：

- `mysql`
- `redis`
- `backend-init`
- `django`
- `fastapi`
- `celery-worker`
- `celery-beat`
- `frontend`

这是一套最贴近仓库当前状态的运行方式。

### 8.2 本地轻量形态

如果只是开发，可以：

- Django 使用 `USE_SQLITE=True`
- FastAPI 单独启动
- Frontend 单独启动
- Celery 按需启动

## 9. 当前开发结论

从代码现状看，这个仓库已经不是“一个抽象平台方案”，而是一个以工作台为中心的写作系统原型，并且以下链路已经可用：

- 登录
- 首页建档
- 书名建议
- 设定向导
- 工作台上下文加载
- WebSocket 章节生成
- 人工正文编辑
- 审阅记录
- 质量提醒
- 章节发布入口

后续继续开发时，应该坚持一个原则：

- 先补齐工作台主路径
- 再扩展旁路模块

否则很容易重新回到“功能很多，但主流程不够顺”的状态。
