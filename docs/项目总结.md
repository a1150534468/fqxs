# 项目总结

## 1. 当前项目状态

截至当前代码，FQXS 已经具备一条可运行的写作主链路，但仍处于“工作台持续打磨”阶段，不适合再按早期文档那种“大而全平台”表述。

更准确的描述是：

- 已形成可登录、可建档、可生成、可编辑、可审阅、可发布入口的写作工作台
- 主产品形态已经从多页面后台，收敛为首页加工作台
- 工作台体验和上下文组织已经明显优先于旁路模块

## 2. 当前已经成型的部分

### 2.1 前端主路径

当前前端主路径很清晰：

- `/login`
- `/`
- `/workspace/:novelId`

其中：

- 首页负责书目、概览、建档
- 工作台负责正文、章节、情报、审阅

这说明系统已经不再依赖大量分散导航页来承载核心价值。

### 2.2 建档体系

当前建档已经形成了完整的草稿转正式项目链路：

- 用户输入灵感
- 创建 `NovelDraft`
- 按步骤生成或填写设定
- 保存 `DraftSetting`
- 完成后转成 `NovelProject` 和 `NovelSetting`

这部分已经能支撑“从空白到可写项目”的第一段流程。

### 2.3 工作台体系

工作台已经具备三块核心能力：

- 章节导航
- 正文写作与流式生成
- 右侧情报与审阅

特别是 `build_workbench_context()` 的存在，说明当前系统已经开始围绕“单项目统一上下文”组织页面，而不是前端拼碎片接口。

### 2.4 生成链路

当前系统已经接通两类 WebSocket 生成：

- 设定流式生成
- 章节流式生成

章节流式生成进一步打通了：

- FastAPI 流式返回
- Django 保存章节
- 自动刷新摘要/一致性/审阅资产

这条链路是当前项目最有完成度的一部分。

### 2.5 审阅与质量控制

审阅系统虽然还不算重型，但已经不再是纯展示。

当前已具备：

- 审阅状态维护
- AI 审读建议
- 修改率估算
- 一致性风险提示
- 发布前校验

尤其是修改率门槛 `15%` 的引入，使得“人工把关”已经从 UI 文案进入了真实流程。

## 3. 当前架构总结

### 3.1 架构分工

当前分工是合理且清晰的：

- React：交互与工作台体验
- Django：业务数据、聚合接口、权限和工作流
- FastAPI：生成与分析
- Celery：异步任务和定时任务
- MySQL/Redis：数据与任务基础设施

### 3.2 技术选型评价

现有技术栈和当前目标是匹配的：

- React + Vite 足够支撑工作台式前端
- Django 很适合承载草稿、项目、章节、审阅等强业务模型
- FastAPI 很适合拆分生成和 WebSocket
- Celery 适合承载发布、异步生成和定时任务

从代码现状看，问题不在选型，而在主路径打磨程度和模块完成度不均。

## 4. 最近一轮整理成果

这一轮最重要的变化，不是加新功能，而是收紧工作台。

### 4.1 右侧情报区去重

右侧区域已经整理成 6 个标签：

- `作品设定`
- `世界观`
- `知识库`
- `手稿道具`
- `质量守护`
- `故事演进`

同时合并了原本重复的区域：

- `审阅定稿` 并入 `质量守护`
- `知识图谱` 并入 `知识库`

这让右栏不再出现“同一类信息多处重复”的问题。

### 4.2 滚动问题修复

工作台中部和右侧此前存在滚动体验问题，特别是：

- 中间正文区上下滑动不顺
- 标签内容区滚动链断裂
- 外层和内层容器互相抢滚动

当前代码已经通过布局收口修复：

- 补齐 `flex` 和 `min-h-0`
- 明确内容区独立滚动
- 统一 Tabs 内容容器结构

这类修改虽然不显眼，但对工作台可用性影响很大。

### 4.3 页面定位更清楚

通过最近整理，三栏职责已经更明确：

- 左边是导航和章节切换
- 中间是唯一正文主航道
- 右边只提供支持信息，不抢正文

这是一个正确的产品方向。

## 5. 当前仍然存在的边界

### 5.1 主路径强，旁路不均衡

现在最强的是：

- 首页建档
- 工作台写作
- WebSocket 生成

相对弱一些的是：

- 灵感模块的前端承接
- 发布链路的最终使用体验
- 统计页面的系统化呈现
- 自动生成计划的前端闭环

### 5.2 有接口，不等于有完整产品

仓库里确实有不少接口和模型，但不代表都已经形成产品能力。

例如：

- `inspirations`
- `stats`
- `tasks`
- `publishing`

这些模块很多都已经有后端基础，但当前前端主体验并不依赖它们成为入口。

### 5.3 默认仍偏开发态

当前默认配置仍明显偏向开发友好：

- `FASTAPI_MOCK_GENERATION=True`
- 默认管理员固定账号密码
- Docker 直接暴露开发端口

这说明仓库当前更适合内部开发、演示和工作流验证，而不是直接视作生产成品。

## 6. 这套代码当前最有价值的地方

从实现角度看，当前仓库最有价值的不是“模块数量多”，而是三点：

- 已经形成写作工作台的骨架
- 已经把 AI 生成与人工改稿放到同一流程里
- 已经开始把项目级上下文、章节级资产、质量级约束统一起来

这三点决定了后续继续迭代时，不需要重做架构，只需要继续打磨主链路。

## 7. 下一阶段最合理的方向

结合代码现状，下一阶段应继续围绕工作台推进，而不是重新发散。

更合理的方向是：

- 继续提升工作台中部写作体验
- 把右侧标签里的信息再做优先级收敛
- 补强连续生成与人工审阅之间的衔接
- 补齐发布前后的反馈链路
- 让统计和任务更多服务当前项目，而不是独立成大后台

## 8. 总结结论

当前项目最准确的阶段判断是：

- 架构已成型
- 主流程已打通
- 工作台正在从“能用”进入“好用”

如果后续继续坚持“以首页到工作台为主链”的策略，这个仓库会比继续扩张外围页面更快进入稳定状态。
