# 项目需求

本文档描述的是“当前代码对应的真实需求范围”，不是早期理想化的全平台需求。

## 1. 产品目标

当前系统的核心目标很明确：

- 让用户从一句灵感快速建档
- 用结构化设定把项目变成可持续写作的项目
- 在一个工作台里完成章节生成、编辑、审阅和情报查看
- 把 AI 写作和人工把关放到同一条主路径上

换句话说，当前产品不是“内容平台后台”，而是“小说写作工作台”。

## 2. 当前必须满足的主流程

### 2.1 登录

系统要求基于 JWT 登录后才能进入主界面。

必须具备：

- 用户登录
- Token 刷新
- 401 自动续期或退回登录页

### 2.2 首页建档

用户进入首页后，应当能完成两件事：

- 查看已有项目
- 通过一句灵感发起建档

因此首页当前需求是：

- 展示书目卡片
- 展示总书籍、总章节、累计字数等概览
- 提供聊天式灵感输入框
- 能从首页直接打开建档向导

### 2.3 建档向导

当前向导的需求不是“十二步大策划”，而是围绕工作台最小可用所需的设定收集。

必须支持：

- 草稿创建
- 书名建议生成
- 世界观生成
- 人物生成
- 地图生成
- 故事线生成
- 情节弧生成
- 开篇生成
- 完成后转正式项目

同时需要满足：

- 每一步可保存
- 前序步骤为后续步骤提供上下文
- 支持流式返回
- 草稿未完成前不转正式项目

## 3. 工作台需求

### 3.1 总体布局

工作台要求使用三栏结构：

- 左栏：章节轨和项目摘要
- 中栏：正文工作区
- 右栏：情报与审阅区

并且需要满足：

- 高度撑满视口
- 各栏可独立滚动
- 三栏宽度可调

### 3.2 左栏需求

左栏当前职责不是复杂树管理，而是章节导航。

必须具备：

- 当前项目摘要
- 当前章节状态
- 章节列表
- 章节点击切换
- 发布入口

### 3.3 中栏需求

中栏是当前产品的主战场，必须支持：

- 单章生成
- 持续迭代
- 续写当前章
- 重写当前章
- 实时流式正文显示
- 流程日志查看
- 人工正文编辑
- 自动保存
- 上一章/下一章切换
- 启动持续迭代时支持每章目标字数、保护上限和全自动模式

中栏还必须展示关键状态：

- 当前是否在生成
- 当前是生成/续写/重写
- 连续生成进度
- 当前章节字数
- 保存状态
- 审阅状态

### 3.4 右栏需求

右栏当前的原则不是“信息越多越好”，而是：

- 信息不要重复
- 信息要围绕当前项目和当前章节
- 信息要能服务写作决策

因此当前需求收敛为 6 个标签：

- `作品设定`
- `世界观`
- `知识库`
- `手稿道具`
- `质量守护`
- `故事演进`

各标签的职责要求如下。

#### 作品设定

展示项目级别的核心写作公约：

- 当前焦点
- 必须保持
- 必须修正
- 连续性提醒
- 优先回收伏笔

#### 世界观

承接建档阶段沉淀下来的设定内容：

- 世界观
- 人物
- 地图
- 故事线
- 情节弧
- 开篇

#### 知识库

承接可检索资产：

- 知识事实
- 伏笔账本
- 知识图谱

#### 手稿道具

必须围绕当前章节展示：

- 本章摘要
- 关键事件
- 开放线索
- 事件卡
- 事实关联
- 角色/地点命中
- 本章伏笔与回收建议

#### 质量守护

必须聚合原本分散的审阅和质量信息：

- 审阅状态
- 审阅意见
- AI 审读建议
- 修改率
- 连续性警报
- 风格风险
- 一致性风险
- 修订动作建议

#### 故事演进

展示项目级的推进资产：

- 当前主线
- 故事线
- 情节点
- 近期章节
- 下一里程碑

## 4. 后端需求

### 4.1 Django 的核心职责

当前 Django 必须承担：

- 用户认证
- 草稿和项目数据保存
- 工作台上下文聚合
- 章节保存与审阅
- 章节发布校验
- 统计聚合
- 任务状态查询
- LLM Provider 管理

### 4.2 FastAPI 的核心职责

当前 FastAPI 必须承担：

- 书名建议生成
- 设定生成
- 章节生成
- 章节续写
- 章节分析
- WebSocket 流式返回
- WebSocket 持续迭代时需要携带本轮写作策略元数据（目标字数、保护上限、是否全自动免审）

### 4.3 Celery 的核心职责

当前 Celery 必须具备：

- 异步生成章节
- 异步发布章节
- 定时抓取灵感
- 定时统计更新

## 5. 数据约束需求

### 5.1 项目

正式项目必须至少具备：

- 标题
- 类型
- 目标章节数
- 当前章节数
- 向导完成状态

### 5.2 章节

章节需要区分：

- `raw_content`
- `final_content`

并需要保留：

- 生成元数据
- 生成上下文快照
- 摘要
- 开放线索
- 一致性状态

### 5.3 审阅

审阅必须独立建模，不能只依赖章节字段。

需要支持：

- `pending`
- `approved`
- `revise`

并需要保留：

- 审阅意见
- AI 审读建议
- AI 动作清单
- 修改率

## 6. 流程约束需求

当前代码已经体现出几个必须遵守的流程约束。

### 6.1 生成与续写约束

- 没选项目时不能生成
- 没选章节时不能续写或重写
- 连续迭代只支持生成新章节
- 目标章节不能小于当前起始章节

### 6.2 审阅约束

- 修改率不足时不能标为已定稿
- 修改率不足时不能发布
- 已有明显风险时应给出提醒或阻塞

### 6.3 发布约束

发布前必须满足：

- 章节状态是 `draft`
- 审阅状态是 `approved`
- 修改率至少 `15%`

## 7. 运行需求

### 7.1 默认运行方式

当前推荐运行方式是 `docker compose`，因为它能一次拉起：

- MySQL
- Redis
- Django
- FastAPI
- Celery Worker
- Celery Beat
- Frontend

### 7.2 本地开发方式

本地开发需要支持：

- Django 用 SQLite 运行
- FastAPI 单独运行
- Frontend 单独运行

## 8. 当前非目标

下面这些内容虽然仓库里有相关代码或雏形，但当前不应当当成主需求目标：

- 把灵感库做成当前前端主导航
- 把发布平台运营后台做成第一优先级
- 把所有分析页面做成独立大模块
- 围绕“多页面后台”继续扩散结构

当前真正的非目标只有一句话：

- 不再扩散平台感页面，优先把工作台主链路打磨完整

## 9. 需求结论

当前代码对应的真实需求可以压缩成一句话：

- 这是一个“围绕章节生产与人工把关”的 AI 小说写作工作台

后续所有新增需求，最好都先判断一个问题：

- 它是否直接增强首页到工作台这条主路径

如果不能，就不应该抢占当前最高优先级。
